- 조사일: 2026-08-16
- 계기: KRX Open API에 **투자자별 거래실적·공매도가 없다**([`krx_open_api.md`](krx_open_api.md) §3.2).
  `flows`는 매일 38요청을 MDC로 보내고 있고, 약관 대상이 남는 유일한 수집기다(K-6).
- 상태: 조사 완료 · **어댑터 구현 완료**(K-6f, 2026-08-16).
  구현하면서 이 문서의 전제 둘이 뒤집혔다 — **§5c를 먼저 읽는다.**

## 3. KIS Developers — 5개를 덮는다

| 우리 metric | KIS 엔드포인트 | TR_ID |
|---|---|---|
| 개인·외국인·기관 순매수 수량 | 종목별 투자자매매동향(일별) | `FHPTJ04160001` |
| 공매도 거래량·거래대금 | 국내주식 공매도 일별추이 | `FHPST04830000` |
| (참고) 시장 단위 | 시장별 투자자매매동향(일별) | `FHPTJ04040000` |
| (참고) 대차 | 종목별 일별 대차거래추이 | 100건/호출 |

근거는 공식 샘플 코드다 —
[`koreainvestment/open-trading-api`](https://github.com/koreainvestment/open-trading-api)
`examples_user/domestic_stock/domestic_stock_functions.py`.

### 3.1 구조가 정반대다 — 그리고 이건 산술 문제가 아니다

```
KRX MDC : (날짜 × 시장) → 전종목      ← 지금
KIS     : (종목)        → 기간
```

| | 현재 | KIS |
|---|---:|---:|
| 논리 슬라이스/일 | 38 | ~5,526 (2,763종목 × 2) |
| 소요 | — | 약 4.6분 (실전계좌 초당 20건) |

`daily_short_sale(J, ticker, 시작일, 종료일)`은 날짜 구간을 받아 종목당 1호출로 이력을 준다 —
**백필은 오히려 이쪽이 빠르다.**

> **초판은 "4.6분이면 끝난다"로 넘어갔다. 그게 문제가 아니다.**
> 외부 리뷰 지적대로 **감사·증분·freshness 모델이 이 구조에서 그대로 성립하지 않는다.**
> 5,526도 실제 HTTP 수가 아니라 **하한**이다 —
> `investor_trade_by_stock_daily`는 continuation token으로 페이징한다.

### 3.1b 전환 조건 — 아래가 갖춰지기 전에는 옮기지 않는다

| # | 문제 | 근거 |
|---|---|---|
| 1 | **증분 cursor를 승계 못 한다** — `Source.KIS`로 바꾸면 source별 `MAX(trade_date)`가 비어 시작점이 사라진다 | `repositories.py` 증분 커서 |
| 2 | **실패 단위가 바뀐다** — (날짜, 시장) 공백에서 **종목별 구멍**으로 | `sync_krx_flows.py` bulk phase |
| 3 | **현행 감사로 재현 불가** — aggregate count + 실패 sample 3건뿐이라 **어느 종목·페이지가 빠졌는지 모른다** | `util/pipeline.py` |
| 4 | **CLI가 `Source.KRX`를 하드코딩**한다 | `cli/app.py` |
| 5 | **freshness도 `Source.KRX` 고정** | `service/freshness.py` |

**전환 조건으로 둘 것**: source별 cursor · 종목·날짜·페이지 checkpoint ·
no-data tombstone · **실 HTTP/retry 계수** · 전역 auth·rate-limit 서킷 브레이커 ·
source-aware freshness.

> **2026-08-28 운영 수정:** 전환 첫날의 빈 KIS cursor를 피하려고 KRX·KIS coverage를
> 합친 구현은 두 collector가 함께 도는 동안 맞지 않았다. KRX 당일 행이 KIS 작업까지
> 완료로 만들었고, `foreign_holding`이 08-20 이후 멈췄다. KRX와 KIS cursor를 각각의
> source로 분리하고, 첫 KIS 실행의 bounded lookback 재수집을 허용하는 쪽으로 고쳤다.

**이게 K-6f의 실제 작업량이다.** 어댑터를 쓰는 것보다 크다.

### 3.2 제약

- **실계좌가 필요하다.** 무료지만 계좌 개설 + API 신청이 선행된다
- 유량 제한: 실전투자 **초당 20건 / 계좌당**, 모의투자 초당 2~5건
- **약관을 읽고 가야 한다.** 증권사 오픈API는 일반적으로 **본인 이용 범위**다.
  연구용 저장은 대체로 그 안이지만 **재배포는 아니다**

### 3.3 자격증명 (2026-08-16 발급 완료)

`KIS_APP_KEY` · `KIS_APP_SECRET` · `KIS_BASE_URL` · `KIS_TIMEOUT_SECONDS`가
**로컬 `.env`에 있다.** prod에는 아직 없고 읽는 코드도 없다.
운영 관점 정리는 `docs/operations.md` "KIS 자격증명" 절.

**토큰 캐시가 구현 시 반드시 걸리는 지점이다.** access token은 유효기간 1일이고
**발급할 때마다 알림톡이 발송된다.** 수집기는 매번 `docker compose run --rm`으로
새 컨테이너를 띄우므로, 컨테이너 안에 캐시하면 **매 실행이 재발급 + 알림톡**이 된다.
`collector` 서비스에 현재 볼륨 마운트가 하나도 없어서
`KIS_TOKEN_CACHE_PATH` + `./state:/state`를 어댑터와 함께 넣어야 한다.

## 4. 갈 곳이 없는 둘

### 4.1 외국인 보유주식수 — **6/7로 올라갈 가능성이 높다** (2026-08-16 갱신)

KIS의 `종목별 외국계 순매수추이`(`frgnmem_pchs_trend`)는 **순매수이지 보유잔고가 아니다.**

> **초판은 여기서 멈추고 "소진율 × 상장주식수로 복원해야 한다"고 적었다.**
> 외부 리뷰가 **공식 KIS checker**에서 더 나은 것을 찾았다 —
> `inquire_price` 응답에 **`frgn_hldn_qty`(외국인 보유수량)가 직접 있다.**
> `hts_frgn_ehrt`(소진율)와 `lstn_stcn`(상장주식수)도 함께 있다.
> 근거: `examples_llm/domestic_stock/inquire_price/chk_inquire_price.py`

**비율 곱셈은 하지 않는다.** 반올림과 분모 시점 때문에 불필요한 오차가 생긴다.
**직접 필드가 있으면 그걸 쓴다.**

- [ ] 발급된 키로 **단위 · null률 · 전종목 coverage**만 확인한다 (K-6b)
- [ ] 확인되면 **`flows` 커버리지는 6/7이고, 남는 건 공매도 잔고 하나뿐이다**

다만 **현재값 endpoint라 과거 이력이 없다.** §1대로 우리는 2007년부터를 이미 갖고 있어
forward-fill만 필요하므로 문제가 되지 않는다.

### 4.2 공매도 잔고 수량

KIS는 공매도 **거래**만 준다. 잔고는 없다. 키움도 확인되지 않았다.
`대차잔고`가 대용으로 거론되지만 **같은 값이 아니다.**

**둘 다 KRX만 만든다.** 남은 경로는 화면 다운로드(수동)와 데이터 상품 구입뿐이다.

## 5. ~~급하지 않다~~ — 철회 (2026-08-16)

> **초판은 "하루 38요청이라 차단을 부른 규모가 아니므로 당장 멈출 이유는 없다"고 적었다.**
> **계획 내부 논리와 충돌한다.** K-0은 차단이 속도가 아니라 **약관 위반**이라 결론냈고,
> 약관 제10조 제2호에는 속도 조건이 없다.
> **38회와 6,000회 사이에 허용·금지 경계가 없다.**
> 호출량은 탐지 위험을 바꿀 뿐 권한을 만들지 않는다.

게다가 그 38이라는 숫자 자체가 **논리 작업 수이지 HTTP 요청 수가 아니다** —
투자자 bulk 1건이 내부에서 4개 엔드포인트를 친다
([`krx_access_inventory.md`](krx_access_inventory.md) §1.1).

**운영 지속 여부는 미결이고 결정이 필요하다** — 같은 문서 §8.1에 정리했다.
계속 돌린다면 근거는 **"요청량이 작아서"가 아니라 "데이터 공백을 감수하지 않기로 한 선택"**이어야 한다.

`flows` 교체의 **기술적** 시급성이 낮은 것은 맞다 — §1대로 2007년부터를 이미 갖고 있어
필요한 건 forward-fill이다. **그건 약관 이야기와 다른 축이다.**

## 5b. 실호출 확인 결과 (K-6b, 2026-08-16)

발급된 키로 직접 호출했다. 토큰 1개만 발급해 캐시 재사용(알림톡 1회).
종목 005930, 조회일 2026-08-14 기준.

### 5b.1 `flows`는 **6/7이다** — 확정

`inquire_price`(`FHKST01010100`) 응답 **80필드**에서 확인했다.

| 필드 | 값 |
|---|---:|
| **`frgn_hldn_qty`** (외국인 보유수량) | **2,736,287,683** |
| `hts_frgn_ehrt` (외국인 소진율) | 46.80 |
| `lstn_stcn` (상장주식수) | 5,846,278,608 |

**검산이 맞는다** — 2,736,287,683 / 5,846,278,608 = **46.80%**.
**비율 곱셈이 필요 없다. 직접 필드를 쓴다.**

### 5b.2 공매도 잔고는 **없다** — 확정

`daily-short-sale`(`FHPST04830000`) `output2` **21필드**를 전부 봤다.
`ssts_cntg_qty`(공매도 거래량) · `ssts_tr_pbmn`(공매도 거래대금) ·
`acml_ssts_*`(누적) · `ssts_vol_rlim`(비중)은 있고 **잔고 필드는 없다.**

**남는 미해결은 `공매도 잔고 수량` 하나뿐이다.**

### 5b.3 `DIV`도 없다 → N7의 C4는 수행 불가 확정

80필드에 `per`·`pbr`·`eps`·`bps`는 있지만 **배당수익률이 없다.**
[`n7_n4_alternatives.md`](n7_n4_alternatives.md) §1.5의 C4는 **폐기 대상이다.**

### 5b.4 이력 깊이 — **2014-04까지 확인.** 우리 표본 시작보다 앞선다

| 엔드포인트 | 확인된 최고(古) | 페이지 크기 |
|---|---|---|
| 공매도 일별추이 | **2014-06-02** | **100행/호출** (구간을 크게 줘도 최신 100행) |
| 종목별 투자자매매동향 | **2014-04-17** | **30행/호출** (`FID_INPUT_DATE_1`이 종료일) |

2020-01 구간만 HTTP 500이 났고 다른 연도는 전부 정상이다 — 일시적 오류로 본다(재확인 필요).

### 5b.5 운영에 영향을 주는 발견 둘

**① 매일 돌 필요가 없다.** 투자자매매동향이 **호출당 30 거래일**을 준다.
주 1회만 돌려도 창이 겹쳐 안전하고, **놓친 날을 자동으로 메운다.**
일 5,526 호출이라는 추정은 **매일 돌린다는 가정**에서 나온 것이다.

**② KIS가 훨씬 세분화된 투자자 구분을 준다.** `output2`가 **101필드**다 —
기관을 **증권·투신·은행·보험·사모·기금·기타법인**으로 쪼개고 순매수 수량과 대금을 모두 준다.
현재 우리는 **기관 통합** 하나뿐이다. 교체가 아니라 **확장 기회**다.
다만 `krx_security_flow_raw`의 metric 체계를 늘리는 것이라 별도 판단이 필요하다.

## 5c. 구현하면서 뒤집힌 것 둘 (K-6f, 2026-08-16)

어댑터를 붙이고 실제로 돌려 보니 **이 문서의 전제 두 개가 틀렸다.**

### 5c.1 유량은 초당 20건이 아니라 **초당 1건**이다

§3.2에 "실전투자 초당 20건 / 계좌당"이라고 적었다. KIS 문서 그대로다.
**이 계정은 그렇게 동작하지 않는다.** 같은 엔드포인트로 rate만 바꿔 측정했다.

| 설정 rate | 성공 | 거부(EGW00201) | 실효 처리량 |
|---:|---:|---:|---:|
| 20 / 10 / 5 /s | 6~7 / 15 | 8~9 | 2.1~3.4/s |
| 1.5/s | 14 / 20 | 6 | 1.09/s |
| 1.2/s | 17 / 20 | 3 | 1.11/s |
| **1.0/s** | **20 / 20** | **0** | 1.05/s |

**핵심은 마지막 열이다.** 어떤 rate를 줘도 실효 처리량이 1.1/s를 못 넘는다.
높게 잡는 것은 성공을 재시도로 바꾸는 것 이상의 의미가 없다.

**§3.1의 "약 4.6분"은 성립하지 않는다.** 2,763종목 기준으로 다시 계산하면

| 작업 | 요청 수 | 소요 |
|---|---:|---:|
| `foreign_holding` 하루치 | 2,763 | **약 46분** |
| `investor` + `shorting` 1회 | 5,526 | **약 1.5시간** |
| 전체 1회 | 8,289 | **약 2.3시간** |

§5b.5의 "매일 돌 필요가 없다"가 여기서 훨씬 중요해진다.
다만 **`foreign_holding`은 예외로 매일 돌려야 한다**(아래).

### 5c.2 유량 초과가 **HTTP 500**으로 온다

`초당 거래건수를 초과하였습니다`(`EGW00201`)가 **429가 아니라 HTTP 500 + 본문**으로 온다.
상태 코드로 먼저 분기하면 전부 일반 서버 오류로 묻힌다 —
**첫 실호출에서 실제로 `http_rate_limited=0`인데 실제 거부는 5건이었다.**
그 상태에서는 rate-limit 서킷 브레이커가 **구조적으로 절대 안 걸린다.**
본문 `msg_cd`를 상태 코드보다 먼저 보도록 고쳤다.

### 5c.3 `foreign_holding`은 최신 거래일에만 수집할 수 있다

§4.1은 `frgn_hldn_qty`를 찾은 것으로 닫았는데, **`inquire-price`에는 기준일 필드가 없다.**
80필드를 다시 확인했다 — 있는 날짜는 52주 최고가 일자 같은 것뿐이다.
따라서 과거 날짜로 요청하면 **오늘 값이 과거 날짜로 저장된다.**

그래서 어댑터는 최신 세션이 아닌 범위에서는 이 그룹을 **아예 건너뛴다.**
결과적으로 **`foreign_holding`만 주 1회로 갈 수 없다** — 놓친 날은 영구 손실이다.
§1의 "필요한 건 forward-fill"이라는 판단은 이 metric에서 가장 날카롭게 적용된다.
